# 网易云音乐歌单评论爬虫

按 **歌单 → 歌曲 → 全量评论 → 匹配目标用户** 的链路，批量抓取某个歌单下所有歌曲的评论，  
并筛选出指定用户（或含指定关键词）的评论。

纯练习项目，用于学习 WeAPI 加密、cursor 分页、并发编排与断点续传。

---

## 一、快速开始

> **依赖是可选的**：本项目的 HTTP 与 AES 都有内置兜底实现，  
> 只要有 Python 3.8+ 就能跑，`pip install` 那一步可以跳过（详见「零安装运行」）。

```bash
# 想装可选依赖（更快、并发连接复用更稳）就执行；没网/装不上也不影响使用
pip install -r requirements.txt

# 环境自检：打印实际使用的 AES/HTTP 后端，并探测能否连上网易云
python web/server.py --check

# 离线自检（不联网，验证加密/分页/去重/续传等共 45 项）
python tests/smoke_test.py

# 小规模试跑：热歌榜前 3 首，每首只抓 1 页
python run.py --playlist 3778678 --all --max-songs 3 --max-pages 1

# 正式用法：在热歌榜里找某个用户的全部评论
python run.py --playlist 3778678 --user 345678901

# 查歌单信息、用户信息、按歌名找歌曲 ID
python run.py --playlist-info 3778678
python run.py --user-info 345678901
python run.py --resolve-song "与我交谈 宋冬野"
```

## 二、网页界面（推荐用法，无需 AI）

项目自带一个本地网页界面：在浏览器里填「歌曲 + 目标用户」就能跑完整链路，  
不用命令行，也**不需要任何 AI 服务**。

零基础直接看 **[使用说明.md](使用说明.md)**；这里是开发者视角的说明。

```bash
# 最省事：双击对应平台的一键启动文件
#   Windows  -> 启动界面.bat
#   macOS    -> 启动界面.command
#   Linux    -> ./start.sh
# 或用统一启动器手动起（三个平台通用）：
python scripts/launch.py              # 默认 http://127.0.0.1:8765/，启动后自动打开浏览器
python scripts/launch.py --port 9000 --no-browser
python scripts/launch.py --check      # 只做环境自检：依赖回退 / 网络连通性

# 也可以直接跑服务本体
python web/server.py --port 9000 --no-browser
```

**不需要装任何第三方库。** 详见下方「零安装运行」一节。

> **关于「打开方式」**：后端服务必须先起来（上面那条命令，或双击 `启动界面.command`），  
> 否则页面只是个空壳——它自己不会发网络请求。
>
> 服务起来之后，页面从哪儿打开都行：后端托管的 `http://127.0.0.1:8765/`、别的本地预览  
> 服务器、甚至直接双击 `web/static/index.html`。前端会自动挨个探测  
> `127.0.0.1:8765 ~ 8775` 找到活着的后端（后端已放行跨源请求），  
> 并在右上角显示「已连接后端 <http://127.0.0.1:8765」。>  
> 如果显示「未连接后端服务」，就是服务没起来，回到上一步即可。

浏览器打开后按四步走：

1. **输入条件** —— 歌曲区支持多行混写：
   | 写法    | 例子                                  | 说明                 |
   | ----- | ----------------------------------- | ------------------ |
   | 歌名    | `向阳而生`                              | 走搜索接口，返回候选列表       |
   | 歌曲 ID | `2006484446`                        | 直接定位               |
   | 网易云链接 | `https://music.163.com/song?id=...` | 歌曲 / 歌单 / 专辑链接都能识别 |
   | 带类型前缀 | `album:156507145`                   | 用于消歧，见下方说明         |
   再填目标用户的 **uid**（最可靠）或**昵称**（可勾选模糊匹配）。两者是"或"关系。
2. **确认曲目** —— 解析出的候选默认全选，可逐条取消勾选；
3. **开始检索** —— 实时显示每首歌的扫描条数、页数、命中数、耗时与速率，随时可停止；
4. **看结果 / 导出** —— 表格展示命中评论（含点赞数、IP 属地、命中原因、楼中楼引用），  
   可导出 CSV（带 BOM，Excel 打开不乱码）或 JSON。

### 为什么它不接 AI 也能自己跑

整条链路都是确定性算法，没有任何一步需要模型推理：

```
歌名 ──► /api/search/get 关键词搜索 ──► song_id
song_id ──► weapi 加密请求 + cursor 翻页 ──► 全量评论
每条评论 ──► user_id == 目标uid ? 昵称 == 目标昵称 ? ──► 命中判定
```

前端只负责展示与轮询（每 0.9 秒拉一次任务快照），全部计算发生在本地 Python 进程里。  
所以它**完全可以自己运行**，除了访问 `music.163.com` 之外不依赖任何外部服务。

### ID 歧义提醒

纯数字 ID 在网易云里是**有歧义**的：歌曲、歌单、专辑的 ID 长得一样，  
没有位数规律可循。实测专辑 `156507145`（《希忘Hope》）与一个歌单 ID 正好撞号，  
不带前缀时会被先当成歌单。因此：

- 不带前缀 → 按 **歌曲 → 歌单 → 专辑** 顺序试探，界面会写明「已按 XX 解析」；
- 想精确指定 → 写 `song:123` / `playlist:123` / `album:123`；
- 最保险 → 直接粘贴网页端地址栏里的完整链接。

### 零安装运行（依赖是可选的）

这个项目原本要装 `requests`（HTTP）和 `pycryptodome`（AES）。但只要换一台电脑，  
"有没有网 / pip 能不能用 / PyPI 通不通"任何一环出问题就跑不起来。所以两者都做成了  
**有则加速、无则回退**：

| 组件      | 装了就用           | 没装则自动改用                                                                                                                                                  |
| ------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTP 通道 | `requests`     | `netease_crawler/http_compat.py` —— 基于标准库 `urllib`，接口对齐 requests（Session / headers / get / post / Response.json / RequestException），支持 Cookie 自动管理与逐请求代理 |
| AES 加密  | `pycryptodome` | `netease_crawler/_aes.py` —— 纯 Python 的 AES-128-CBC                                                                                                      |

回退不是"降级凑合"，两条路径的密文**逐字节一致**，并由 `tests/smoke_test.py` 用  
FIPS-197 与 NIST SP 800-38A 官方测试向量交叉校验。想确认当前用的是哪条路径：

```bash
python web/server.py --check      # 打印后端 + 探测 music.163.com 连通性
```

结论：**目标机器只要有 Python 3.8+，不需要装任何东西，也不需要联网装包。**

## 三、实测接口结论（重要）

网上（包括很多教程和那张架构图）对这套接口有几处**不准确**的描述。以下结论均在 2026-09  
对真实接口实测得到，代码已按实测行为实现：

| 项目            | 流传说法                     | **实测结果**                                                                                                                                                  |
| ------------- | ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 加密方式          | 用 `cloudmusic.encrypt` 库 | 可自行实现：AES-128-CBC **双层** + 裸 RSA 模幂。RSA 用标准库 `pow()` 即可；AES 装了 `pycryptodome` 就用它，没装则用内置的纯 Python 实现                                                      |
| `pageSize`    | "最大可设置为 1000"，也有人写 10000 | 上限确实是 **1000**。传 2000 / 5000 服务端**静默压回 1000** 且不报错                                                                                                        |
| 翻页参数          | 用 `cursor` 时间戳           | 正确，但 **`pageNo` 被服务端完全忽略**。只认 `cursor`，`offset` 也有效                                                                                                       |
| `hasMore`     | 用它判断是否还有下一页              | ⚠️ **恒为 `False`**，即使后面还有上百万条。照它写会只爬到 1000 条就停                                                                                                             |
| 终止条件          | —                        | 必须自行判断：① 返回空页 ② `cursor` 不再前进（防死循环）③ 达到 `max_pages`                                                                                                       |
| `orderType`   | 1=推荐 2=热度 3=时间           | 1/2/3 返回结果**完全相同**（都是按时间倒序）                                                                                                                               |
| `orderType=0` | "从最早评论开始正序翻"             | ⚠️ **不可用于爬取**：只返回首页部分数据（实测某歌 649 条 / 实际 1648 条），之后回传 cursor 或增大 offset **都返回空**，且不报错。即静默丢数据                                                               |
| 歌单曲目          | 用 `playlist/track/all`   | 该接口在 weapi 下 **404**。正确做法是 `weapi/v6/playlist/detail` 取 `trackIds`                                                                                        |
| 歌单曲目完整性       | —                        | `trackIds` 返回**完整**列表（实测 9816/9816 全给），但 `tracks` 明细会被截断到约 10 条 → 曲目信息必须另用 `v3/song/detail` 批量取                                                           |
| 找某用户的评论       | "直接筛用户评论"                | 不存在"用户评论历史"接口（`user/comment/history` 返回 **404**）。只能按歌单/歌曲暴力扫描后用 uid 过滤                                                                                    |
| 按昵称搜用户        | —                        | ⚠️ 匿名状态下 `type=1002` 搜索**恒返回 0 条**（weapi 与明文通道、多种关键词都试过）。拿 uid 请去网页端用户主页 URL 里取 `id=`                                                                     |
| 按歌名搜歌曲        | —                        | 明文通道 `GET /api/search/get?type=1` **可用**（`--resolve-song` 就是走这条）；weapi 的 `cloudsearch` 匿名态易被风控                                                            |
| `ipLocation`  | 字符串                      | 实际是 **dict**：`{"location": "江苏", ...}`，需取 `.location`                                                                                                     |
| `timeStr`     | 可直接展示的绝对时间               | ⚠️ 实际是**相对时间**：近处给 `"昨天12:25"` / `"3天前"`，远处只给 `"2017-04-14"` 这种日期。**不能直接展示，更不能拿去排序**（按字符串排会完全错乱）。务必用 `time`（毫秒戳）自行换算绝对时间，原始 `timeStr` 仅作留档（存到 `time_rel`） |

### 速度实测

- 单页 1000 条约 **2 秒** → 单线程约 **500 条/秒**
- 实测 3 线程并行 3 首歌 3000 条评论耗时 **3.4 秒**（≈ 880 条/秒）

> ⚠️ **量级提醒**：热门歌曲评论量极大（周杰伦《晴天》约 **197 万条**），  
> 按 500 条/秒单线程需要约 66 分钟/首，全量扫描一个千首歌单不现实。  
> 建议优先用 `--max-pages`、`--stop-on-found` 缩小范围，或用 `--order` 选择从新/从旧开始。

### 实测案例：宋冬野《与我交谈》

```bash
python run.py --resolve-song "与我交谈 宋冬野"   # → song_id=3400414874
python run.py --song-ids 3400414874 --all        # → 1648 条评论 / 3.8 秒
```

| 验证项      | 做法                                             | 结果                                   |
| -------- | ---------------------------------------------- | ------------------------------------ |
| 爬取完整性    | 用 pageSize=1000 与 pageSize=100 各爬一遍，比对评论 ID 集合 | 两次均为 **1648 条，集合完全相同**               |
| 服务端计数可信度 | 对比 `totalCount` 与实际                            | `totalCount=1602`，实际 **1648**，服务端值偏小 |
| 降序是否覆盖升序 | 升序首页 649 条与降序 1648 条求包含关系                      | 升序 ⊆ 降序，升序独有 **0** 条                 |
| 匹配精确性    | 拿示例 uid `123456789` 跑一遍，与全量库 SQL 真值比对          | 工具输出 13 条 = 真值 13 条，**集合完全一致**       |

## 五、加密原理

WeAPI 只加密 `params` 和 `encSecKey` 两个表单字段：

```
原文 JSON ──AES-CBC(key1)──> base64 ──AES-CBC(key2)──> params
随机 key2 ──RSA(公钥)────────────────────────────────> encSecKey

key1 = "0CoJUm6Qyw8W8jud"（固定）
key2 = 每次随机的 16 位字符
IV   = "0102030405060708"（固定）
```

RSA 部分没有用标准 PKCS#1 填充，只是把明文**倒序**后当作大整数做 `m^e mod n`，  
再左补零到 256 位十六进制——所以用标准 RSA 库反而对不上，直接 `pow()` 即可。

## 六、并发与可靠性设计

| 机制   | 做法                                      | 解决的问题                                                                 |
| ---- | --------------------------------------- | --------------------------------------------------------------------- |
| 并发维度 | 歌曲之间并行，**单首歌内串行**                       | cursor 分页必须顺序推进，强行并发会重复抓                                              |
| 线程安全 | 每线程独立 `requests.Session`                | Session 非线程安全，共享会串 cookie/socket                                      |
| 全局限速 | 跨线程共享最小请求间隔阀                            | 避免"线程数 × 单线程速率"放大总 QPS 触发风控                                           |
| 自动重试 | 识别 `-460`/`-462`/429/5xx/非 JSON 页面，指数退避 | 风控与网络抖动                                                               |
| 幂等去重 | `comment_id` 主键 + `INSERT OR IGNORE`    | 重试、续传造成的重复抓取                                                          |
| 断点续传 | 每页落一次 `cursor`，完成后标 `done`              | 进程被杀/中断后按歌曲粒度续爬                                                       |
| 单曲隔离 | 单曲异常不抛出线程池                              | 一首歌失败不会拖垮整个歌单                                                         |
| 截断检测 | 末页恰好满 `page_size` 即告警                   | 服务端限流时会**静默停在满页处**——不报错、不返回空页，只是不再前进。实测 6 并发扫同一张专辑，有 3 首各少 3~4 万条（见下） |

> **实测案例（并发限流截断）**：扫描华晨宇《希忘Hope》专辑 11 首、约 150 万条评论时，  
> 用 6 线程并发，其中 3 首的末页**恰好是 1000 条的整数倍**（72000 / 84000 / 115000 条），  
> 而其余 7 首末页都有零头（如 123287 = 123×1000 + 287）。单线程重扫这 3 首后分别回到  
> 114563 / 116286 / 129177 条，**末页全部变成非整数**——证明整数倍就是"在满页处被掐断"。  
> 抽样重扫 2 首非整数倍的歌，条数与并发轮**完全一致**（117028 / 117229），确认它们未受影响。  
> 结论：**末页是否为整页，是判断单曲抓取是否完整的可靠信号**，现已内置为自动告警。

## 七、常用参数

| 参数                       | 说明                                                                           |
| ------------------------ | ---------------------------------------------------------------------------- |
| `--playlist ID`          | 歌单 ID                                                                        |
| `--song-ids 1,2,3`       | 直接指定歌曲 ID（与 `--playlist` 二选一）                                                |
| `--user UID`             | 目标用户 uid，逗号分隔多个（**最可靠**）                                                     |
| `--nickname 昵称`          | 按昵称精确匹配（重名多，仅作辅助）                                                            |
| `--keyword 关键词`          | 按评论正文关键词匹配                                                                   |
| `--all`                  | 不筛选，全部保存                                                                     |
| `--order newest\|oldest` | 结果排列顺序。**爬取方向恒为降序**（orderType=0 翻不动页），`oldest` 只影响导出排序，且不能与 `--max-pages` 连用 |
| `--workers N`            | 并发线程数，默认 4                                                                   |
| `--interval S`           | 全局最小请求间隔，默认 0.35s，调大更安全                                                      |
| `--max-pages N`          | 单首歌最多翻页数，0=不限                                                                |
| `--max-songs N`          | 最多处理多少首歌                                                                     |
| `--stop-on-found`        | 单曲内命中即停（提速，但会漏掉后续命中）                                                         |
| `--cookie "MUSIC_U=..."` | 登录 Cookie，可显著降低风控概率                                                          |
| `--no-resume`            | 忽略已有进度重爬                                                                     |

## 十、常见问题

**Q：只爬到 1000 条就停了？**  
检查是否误用了 `hasMore`——它恒为 `False`。本项目已按空页/cursor 停滞判断，不会出现这个问题。

**Q：用 `--order oldest` 想抽样"最早的 1000 条"报错了？**  
不是 bug，是接口限制。orderType=0 只返回首页部分数据且无法续翻（cursor 和 offset 都试过），  
所以"只要最早的 N 条"在接口层面做不到。要么全量爬完再按时间正序导出，要么改用 `--order newest` 抽样。

**Q：`--resolve-user` 搜不到人？**  
网易云用户搜索接口匿名状态下恒返回空。直接在网页端打开用户主页，从 URL  
（`music.163.com/user/home?id=xxxxx`）里取 uid 即可。搜歌曲用 `--resolve-song` 是可以的。

**Q：评论总数对不上？**  
`totalCount` 只是服务端的近似值。实测某歌 `totalCount=1602`，实际抓到 **1648** 条  
（用 pageSize=1000 和 100 两种尺寸交叉验证，结果一致），以实际抓到的为准。

**Q：歌单曲目数对不上 `trackCount`？**  
该歌单可能限制匿名访问完整曲目，试试 `--cookie` 带上登录态。

**Q：出现 `code=-460`？**  
触发风控。调大 `--interval`、降低 `--workers`，或加 `--cookie`。

**Q：没报错，但某个歌抓到的条数明显偏少，末页又正好是 1000 条？**  
典型的**并发限流静默截断**。服务端不会报错、也不返回空页，只是不再往回给数据，  
于是翻页循环"正常"结束，数据却少了一截。判断方法就一条：  
**自然结束时末页必定不满 `page_size`**（如 123287、117028），  
末页恰好等于 1000 就是被掐断（如 72000、84000、115000）。


本项目已在单曲抓取结束时自动检测并告警。处理办法：降低 `--workers`（实测 2~3 安全、6 会中招）后重跑该曲。
